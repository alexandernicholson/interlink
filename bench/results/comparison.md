# Service Mesh Benchmark Comparison

HTTP workload comparison. Measurement dates from Fortio `StartTime`: 2026-07-08.

For the separate native Veyrmux-versus-stock-Yamux lifecycle result, see [Benchmark Results](../../docs/benchmarks/results.md). Regenerating this HTTP report does not recapture that runtime A/B; use the dates and raw inputs below to identify these measurements.

Generated by `bench/scripts/aggregate.py` from Fortio JSON and metrics CSVs: [interlink](interlink/), [linkerd](linkerd/), [istio-ambient](istio-ambient/). Each Fortio file records its start time, duration, connection count and load settings.

Harness topology: the same 3-node kind layout (`bench/manifests/kind-3node.yaml`) in a separate cluster per mesh, with load generator and echo server on separate workers. The configured workload is Go HTTP echo with a 200 ms delay and 1 KB payload; CPU/memory are sampled via `kubectl top pod`. interlink and Linkerd use per-pod sidecars; Istio ambient uses node-level ztunnel. Shared topology and workload do not make these identical deployment architectures.

A profile is **valid** only if achieved RPS reaches at least 97 % of target, there are zero reported errors, and peak host CPU stays below 85 %. Invalid profiles are excluded from the tables; the reason identifies the error, under-target load, or host saturation.
