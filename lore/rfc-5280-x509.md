## 1. Summary

RFC 5280 profiles the X.509 v3 certificate format for Internet use. It defines the certificate fields, standard extensions, certification path validation algorithm, and CRL profile. For interlink, the critical sections are: (1) the Subject Alternative Name extension (§4.2.1.6) which carries the SPIFFE identity, (2) the name constraints and key usage extensions for policy enforcement, and (3) the certification path validation algorithm which we adapt for short-lived certs.

## 2. Key Sections

| Section | Lines | Content |
|---------|-------|---------|
| 4.1 Basic Certificate Fields | 850-1050 | tbsCertificate + signatureAlgorithm + signatureValue |
| 4.1.2.4 Subject DN | 1150-1200 | Subject DN encoding — we use empty sequence (§4.2.1.6:1985) |
| 4.2.1.6 Subject Alternative Name | 1953-2070 | **THE key section** — URI encoding for SPIFFE IDs |
| 4.2.1.3 Key Usage | 1430-1460 | digitalSignature, keyEncipherment — our usage |
| 4.2.1.12 Extended Key Usage | 2100-2160 | serverAuth + clientAuth for mTLS |
| 4.2.1.9 Basic Constraints | 1900-1940 | CA:FALSE for leaf certs |
| 4.2.1.10 Name Constraints | 2160-2280 | Restrict which SPIFFE IDs a CA can issue |
| 6 Certification Path Validation | 3800-4200 | Chain building algorithm — adapted for single-level |
| 10 Security Considerations | ~6200 | Private key protection, path validation, name constraints |

## 3. Implementation Plan

### 3.1 Certificate Structure

```rust
/// An X.509 v3 certificate as defined in RFC 5280 §4.1
pub struct Certificate {
    tbs_certificate: TbsCertificate,
    signature_algorithm: AlgorithmIdentifier,
    signature_value: Vec<u8>,
}

pub struct TbsCertificate {
    version: u8,                        // 2 = v3
    serial_number: Integer,             // §4.1.2.2 — random 8 bytes
    signature: AlgorithmIdentifier,     // matches outer signatureAlgorithm
    issuer: Name,                       // CN=interlink CA
    validity: Validity,                 // notBefore, notAfter
    subject: Name,                      // EMPTY — identity in SAN (§4.2.1.6:1985)
    subject_public_key_info: SubjectPublicKeyInfo,
    issuer_unique_id: Option<Vec<u8>>,  // NOT used in v3
    subject_unique_id: Option<Vec<u8>>, // NOT used in v3
    extensions: Vec<Extension>,         // at minimum: SAN, KU, EKU, BC
}
```

### 3.3 Certificate Validation (adapted for short-lived)

```
Algorithm 1: ValidatePeerCertificate (adapted from RFC 5280 §6)

1. Verify certificate validity period (notBefore ≤ now ≤ notAfter)
   → Skip if cert is within 1h window (clock skew allowance)

2. Verify signature using issuer's public key
   → Ed25519 for interlink certs

3. Verify Basic Constraints: CA must be FALSE for leaf certs

4. Verify Key Usage: MUST include digitalSignature
   Check EKU: MUST include serverAuth OR clientAuth (RFC 5280 §4.2.1.13)

5. Extract subjectAltName → parse SPIFFE URI
   → If subjectAltName is missing: REJECT (RFC 5280 §4.2.1.6:1982-1985)
   → If subject DN is non-empty: ALLOW (but warn — our CAs set empty)

6. Verify no CRL needed (certs are short-lived — expiry IS revocation)
   → Skip CRL check entirely. This is an interlink policy decision.

7. Verify chain up to trust anchor:
   parent_pub_key.verify(cert.signature, cert.tbs_der)
   → Repeat for each intermediate (max chain depth = 2: leaf + CA)
```

## 4. Edge Cases

| Issue | RFC Reference | Mitigation |
|-------|---------------|------------|
| Empty subject + missing SAN | §4.2.1.6:1982-1985 | REJECT — our CA always sets SAN |
| SAN with empty URI | §4.2.1.6:2065-2070 | REJECT — not permitted |
| Certificate with CA:TRUE for leaf | §4.2.1.9 | REJECT — pathLenConstraint=0 for intermediates |
| Unknown critical extension | §4.2 | REJECT — per RFC 5280, unknown critical = reject |
| Signature algorithm mismatch | §4.1.1.2/§4.1.2.3 | The tbsCertificate.signature MUST match outer signatureAlgorithm |
| Expired cert from clock skew | §4.1.2.5 | Allow 1h grace on both sides |

## 5. Compliance Checklist

### MUST
- [ ] Encode SPIFFE ID as uniformResourceIdentifier in subjectAltName (§4.2.1.6:2030)
- [ ] Set subject DN to empty sequence (§4.2.1.6:1982-1985)
- [ ] Mark subjectAltName as critical when subject is empty (§4.2.1.6:1987)
- [ ] Include Key Usage Extension with digitalSignature (§4.2.1.3)
- [ ] Include Extended Key Usage with serverAuth + clientAuth (§4.2.1.12)
- [ ] Include Basic Constraints with CA:FALSE for leaf certs (§4.2.1.9)
- [ ] Verify certificate signature using issuer's public key (§6)
- [ ] Reject certificates with unknown critical extensions (§4.2)

### SHOULD
- [ ] Use Ed25519 signatures (not in RFC 5280 — it's from RFC 8410)
- [ ] Set serial number to at least 8 bytes of random data (§4.1.2.2)
- [ ] Support pathLenConstraint for intermediate CAs (§4.2.1.9)
- [ ] Verify certificate validity period with 1h clock skew allowance (§4.1.2.5)

### MAY
- [ ] Support CRLs for long-lived intermediate CA certs (§5)
- [ ] Support Authority Information Access for CA discovery (§4.2.2.1)
